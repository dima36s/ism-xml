# ИСМ XML

Веб-приложение для машиночитаемых регламентов интегрированной системы менеджмента (ИСМ). Загружаете документы — Word (.docx и старый .doc), PDF, схемы Visio (.vsdx), Excel-реестры или XML ИСМ — приложение размечает пункты и атомарные требования, делит их на бизнес- и системные, заводит на каждое требование карточку корпоративного реестра, собирает карточки всех документов в общий реестр, строит граф требований по уровням документов и подсвечивает пересекающиеся требования. Результат выгружается в XML и Excel.

Для примера в приложении опубликована методика **C2.4.1.MTH.01 «Методика по разработке функциональных моделей информационных систем»**, версия 1.0, статус «проект». Без входа она открывается сразу; с личным кабинетом её требования заложены в общий реестр, а сам документ открывается по ссылке «открыть регламент C2.4.1.MTH.01» на пустой главной.

**Открыть приложение:** https://dima36s.github.io/ism-xml/

Два режима работы:

- **Без входа** (пока в `assets/config.js` не указан проект Supabase): документы и правки хранятся только в браузере пользователя (IndexedDB).
- **С личным кабинетом** (проект Supabase подключён): регистрация и вход по почте и паролю (без подтверждения почты), документы хранятся в базе данных, у каждого пользователя свои; новый пользователь начинает с пустого рабочего пространства. Общий реестр требований — один на всех, хранится в базе, пополняется автоматически без повторов. Настройка — в разделе [«База данных и вход»](#база-данных-и-вход-supabase).

## Как пользоваться

1. **Загрузка.** На главной странице перетащите файлы в рамку или нажмите «Загрузить» в верхней панели. Можно несколько файлов сразу; файлы можно бросить и в любое место страницы. Один файл сразу открывается на вкладке «Документ».
2. **Вид документа.** Вид (политика, положение, регламент, методика…) определяется по обозначению и заголовку; его можно поменять в карточке документа на главной. Документы сгруппированы по уровням иерархии.
3. **Документ.** Текст с исходной нумерацией, под каждым пунктом — найденные требования. Кнопка «Разметка: добавить требование» показывает у каждого пункта кнопку для ручного добавления. Рисунки и схемы открываются щелчком в просмотрщике: масштаб кнопками, колесом мыши с Ctrl или клавишами +/−, перетаскивание, листание, скачивание.
   Схема Visio становится документом: каждая страница — раздел с рисунком схемы, под ним таблица «Участник — Действие» из дорожек и шагов внутри них и остальные надписи фигур.
4. **Карточка.** Кнопка «Изменить» открывает карточку реестра: формулировка, цитата, тип (бизнес или системное), владелец, критичность C1–C4 с обоснованием, область применения, метод верификации, критерий приёмки, уровень, статус, версия и основания — требования вышестоящих документов. Поля, без которых карточка остаётся «Заполнить», отмечены точкой.
5. **Общий реестр.** Без входа — карточки всех документов этого браузера, отмеченных «в общем реестре», с фильтрами по документу, уровню, типу, владельцу, критичности, комплектности и пересечениям. С личным кабинетом — один реестр на всех пользователей из базы данных (см. [«Общий реестр в базе»](#общий-реестр-в-базе)); кнопка «Выгрузить в Excel» скачивает его целиком или найденные записи.
6. **Граф требований.** Полосы уровней 1–4 и внешней документации, документы в своих полосах, требования внутри документов, связи-основания между ними. Приложение предлагает основания по сходству формулировок — их принимают одной кнопкой.
7. **Пересечения.** Пары похожих требований: «почти совпадают», «пересекаются», «противоречат по модальности». Ложные пары отмечаются «не дубль».
8. **Обмен с коллегами.** Меню «Выгрузить»: XML документа, реестр документа в Excel, общий реестр в Excel (без входа — ещё и в XML), документы одним архивом. Коллега загружает полученный XML у себя.

## Иерархия документов

| Уровень | Вид документа | Код | Назначение |
|---|---|---|---|
| 1 — стратегическое управление, принятие решений, контроль деятельности | Политика | GPL | Общие требования, широкая область применения, низкая детализация |
| | Цели | GOAL | Официально зафиксированные ожидаемые результаты деятельности |
| | Руководство | GDL | Руководящие принципы и основные направления развития |
| 2 — управление деятельностью применительно к процессам | Положение | PLC | Общие правила и требования к направлению деятельности/процессу — что делаем |
| | Процедура | PCD | Этапы процесса, сроки, ответственность, требования к результату — как делаем |
| | Стандарт | STD | Требования к процессу верхнего уровня и его реализации |
| | Регламент | RGL | Состав, структура и порядок управления процессом |
| | Стандартная операционная процедура | SOP | Схема процесса, роли и краткое описание на одну-две страницы |
| 3 — исполнение деятельности | Методика | MTH | Приёмы, техники, технологии и инструменты практических действий |
| | Инструкция | INS | Порядок и способы выполнения действий |
| 4 — свидетельства о выполнении требований | Записи и отчёты | REC | Шаблоны, чек-листы, журналы, реестры, перечни |
| — | Внешняя документация | EXT | Законы, постановления, ГОСТы, ОСТы, СНиПы, ТУ |

У записей и внешней документации в классификаторе нет кода, поэтому приложение использует REC и EXT. Основанием требования может быть только требование документа выше по иерархии или внешней документации.

## Бизнес- и системные требования

**Бизнес-требование** относится к процессу, участникам, подразделениям и документам («владелец процесса должен утвердить ФМ»). **Системное требование** — к информационной системе: её функциям, данным, интерфейсам и качеству работы («система должна автоматически формировать отчёт», «время отклика не должно превышать 2 с», «пользователь должен иметь возможность выгрузить реестр»).

При разметке тип определяется правилами: если подлежащее требования — система, модуль, приложение, интерфейс, база данных, или в тексте есть признаки поведения системы (автоматически, авторизация, интеграция, резервное копирование, время отклика), требование системное, иначе — бизнес. Определённый автоматически тип отмечен пунктирной рамкой; после выбора в карточке он считается подтверждённым. В XML тип хранится в `requirement/@category` (`business` | `system`) и `@categoryStatus`, в Excel — в дополнительном столбце S.

## Что умеет разметка

| Источник | Что получается |
|---|---|
| Word .docx | Разделы и пункты по стилям заголовков и нумерации Word, таблицы, термины, сводная информация и история изменений в метаданные |
| Word 97–2003 .doc | То же, что .docx: текст, таблицы, заголовки и автоматическая нумерация пунктов читаются из двоичного формата прямо в браузере. Файлы Word 6.0/95 и защищённые паролем не читаются |
| Visio .vsdx | Страница — раздел с отрисованной схемой (SVG): фигуры, соединители со стрелками, группы, мастер-фигуры трафаретов, текст. Дорожки и шаги в них — таблица «Участник — Действие», из неё — требования «кто что делает». Старый двоичный .vsd нужно пересохранить в Visio как .vsdx |
| PDF | Разделы и пункты по нумерации в тексте; таблицы и рисунки не восстанавливаются |
| Excel-реестр .xlsx | Каждая строка листа с заголовками шаблона V0.1 — карточка со всеми полями A–R (и S, если есть) |
| XML ИСМ | Открывается как есть, без повторной разметки |

Требование выделяется двумя способами.

- **По модальному слову** («есть в тексте»): «должен», «следует», «необходимо», «обязан», «обязательны для исполнения», «не допускается», «запрещается», «нельзя», «рекомендуется», «допускается», «вправе». Фраза «A должен X, а также Y» делится на два требования.
- **По описательной формулировке** («модальность выведена»), как обычно пишут регламенты:
  - действие роли в настоящем времени — «ФЗ утверждает ФМ», «Юридический отдел рассматривает проект договора»;
  - страдательный залог — «проект договора согласовывается…», «функции приводятся с указанием ограничений»;
  - «ответственность за… несёт…», «особое внимание уделяется…» (рекомендация);
  - перечень после вводной фразы с «включает», «состоит из», «содержит» или под заголовком «Требования к…», «Принципы…», «Задачи…» — отдельное требование на каждый пункт;
  - таблица ответственности («Участник | Функция», «Этап | Ответственный | Срок») — отдельное требование на каждую функцию;
  - в разделах с требованиями и правилами — ещё и формулировки «Ключевым элементом… является…», «…включает…», краткие причастия («чётко сформулированы ограничения»), пункты-действия («обозначение форматов хранения данных»).

  Термины, область применения и нормативные ссылки так не размечаются, определения вида «X — это…» не считаются требованиями.

На методике C2.4.1.MTH.01 разметка из Word находит 96 % требований эталонного XML (46 из 48; до появления описательных правил — 29 %), из PDF — 81 %: таблицы в PDF не восстанавливаются. Дословная цитата сохраняется в `<quote>` и проверяется по тексту пункта. Каждой новой карточке присваивается рабочий номер `TEMP-ГГГГММДД-NNN`, статус «Черновик» и версия 0.1.

Пересечения и предложенные основания ищутся по словам формулировок без учёта окончаний (стеммер Snowball для русского языка) с весами TF-IDF: редкие слова значат больше, частые — меньше. Это сходство слов, а не смысла: требования, сказанные разными словами, могут не найтись.

## Реестр требований

Карточка требования в XML (`<requirement>` с `<registry>`) повторяет шаблон мастер-реестра пилота V0.1. Выгрузка в Excel даёт столбцы A–R в том же порядке, со списками допустимых значений и формулой комплектности — строки можно вставлять в мастер-реестр как есть. Столбцы S (тип требования) и T (основание) — дополнительные. Общий реестр в XML — один документ ИСМ: раздел на каждый источник, основания — `semanticLinks` с отношением `implements`, пересечения — замечания `duplicate` и `inconsistency`.

## База данных и вход (Supabase)

Приложение статическое и работает на GitHub Pages; база данных и учётные записи — в проекте [Supabase](https://supabase.com) (PostgreSQL и Supabase Auth). Схема лежит в `supabase/setup.sql`.

> **Где хранятся данные.** Облачный Supabase размещает базу за пределами России. Почты пользователей — персональные данные; учитывайте 152-ФЗ и правила компании. Supabase с открытым кодом можно развернуть на своём сервере (Docker) — приложение работает с ним так же, достаточно указать его адрес.

### Таблицы

| Таблица | Что хранит |
|---|---|
| `document_levels`, `document_types` | Справочник иерархии документов: 4 уровня, 12 видов (заполняется скриптом) |
| `documents` | Документы пользователя: вид, обозначение, версия, исходный файл, XML ИСМ, участие в общем реестре |
| `requirements` | Атомарные требования и поля карточки реестра: тип, критичность, владелец, критерий, статус, комплектность |
| `requirement_links` | Основания между требованиями разных документов — рёбра графа |
| `overlap_dismissals` | Пары, отмеченные «не дубль» |
| `user_settings` | Счётчик номеров TEMP, последний открытый документ |
| `profiles` | Профиль личного кабинета; пароли хранит Supabase Auth в `auth.users` |
| `registry_entries` | **Общий реестр** — один на всех пользователей: столбцы A–T мастер-реестра, документ-источник, кто добавил |

Представления `documents_level_1` … `documents_level_4`, `documents_external` показывают документы по уровням; `v_registry` — реестр по документам пользователя; `v_document_stats` — число бизнес- и системных требований по документам. Политики Row Level Security пускают каждого пользователя только к его строкам; общий реестр читают все вошедшие пользователи, а пополняют его только функции `registry_sync` и `registry_remove`.

### Общий реестр в базе

- **Пополняется сам.** Когда пользователь загружает документ с включённым переключателем «в общем реестре» или правит его карточки, требования документа записываются в общий реестр. Исключение документа из реестра или его удаление убирает его записи.
- **Без повторов.** Требование не добавляется, если в реестре уже есть тот же документ (обозначение ИСМ, например C2.4.1.MTH.01) с тем же номером требования, та же формулировка (без учёта регистра, пунктуации и «ё») или почти та же — те же слова с точностью до окончаний, те же числа и модальность. Документ с обозначением, которое уже добавил другой пользователь или которое опубликовано, второй раз не добавляется; вторая копия документа у одного пользователя тоже.
- **Чьи записи.** Запись принадлежит тому, кто первым добавил документ: обновить или убрать её может только он. Требования C2.4.1.MTH.01 заложены скриптом и не меняются из приложения. Документ без обозначения ИСМ — свой у каждого пользователя, повторы его формулировок отсекаются так же.
- **Выгрузка.** Вкладка «Общий реестр» загружает записи из базы; «Выгрузить в Excel» даёт файл в формате мастер-реестра (столбцы A–T).

### Подключение

1. Создайте проект на supabase.com.
2. **SQL Editor** → вставьте `supabase/setup.sql` целиком → **Run**. Скрипт можно запускать повторно; после обновления приложения запустите новую версию — она добавит недостающие таблицы и функции, данные пользователей не трогает. При первом запуске версии с общим реестром из документов пользователей убираются копии опубликованного регламента (без правок): его требования теперь в общем реестре.
3. **Authentication → Sign In / Providers → Email**: провайдер Email включён, **Confirm email выключено**, минимальная длина пароля — 8. Приложение не подтверждает почту и не отправляет писем: почта служит логином, свой почтовый сервер (SMTP) не нужен.
4. **Authentication → URL Configuration**: Site URL — адрес приложения, например `https://dima36s.github.io/ism-xml/`.
5. **Project Settings → API Keys**: скопируйте Project URL и ключ publishable (`sb_publishable_…`, в старых проектах — `anon`) в `assets/config.js` и сохраните в репозиторий. Этот ключ публичный по замыслу Supabase — доступ ограничивают политики из `setup.sql`. Секретный ключ (`sb_secret_…`, `service_role`) и пароль базы данных в приложение класть нельзя.

После этого приложение открывается экраном входа: регистрация по почте и паролю сразу открывает рабочее пространство. Если пользователь забыл пароль, администратор удаляет его в **Authentication → Users**, и пользователь регистрируется заново (его документы и добавленные им записи общего реестра при этом удаляются). Документы, загруженные в браузере до входа, приложение предложит перенести в личный кабинет.

## Как обновить опубликованный регламент

1. Отредактируйте `data/C2.4.1.MTH.01.machine-readable.xml`.
2. Сохраните изменения в `main`. GitHub Actions проверит XML: соответствие XSD, цитаты требований в тексте пунктов, отсутствие ФИО.
3. Через минуту-две изменения появятся по ссылке приложения.

Локально ту же проверку запускает `python tools/validate.py data` (нужен `pip install lxml`). Правки, сделанные в приложении, видны только их автору; чтобы опубликовать их для всех, выгрузите XML и замените им файл в `data/`.

## Работа без интернета

В меню «Выгрузить» выберите «Комплект документа архивом», распакуйте и запустите `build.bat`. Скрипт проверит XML и соберёт рядом HTML-страницу.

## Конфиденциальность

Репозиторий публичный. В опубликованном регламенте ФИО сотрудников удалены. Файлы разбираются в браузере. В режиме без входа документы и правки хранятся только в этом браузере; в режиме с входом — в базе данных подключённого проекта Supabase, доступ к ним есть только у владельца учётной записи.
